Project Atlas

An interactive developer-operations workspace for understanding app health, deployments, failures, and performance—and eventually investigating incidents with AI.

← Current roadmap · Planning stage · November 19, 2026

The problem and goal

Developers often jump between uptime checks, server logs, deployment history, and metrics when something breaks. The data exists, but reconstructing what happened takes time.

Goal: bring operational evidence into one understandable view, then help explain failures without inventing causes.

Potential users: solo developers, student teams, and small teams operating deployed apps. These users are proposed, not validated.

A realistic workflow

  1. Connect an app or API and configure a simple health check.
  2. See whether it is responding, recent response times, and when checks failed.
  3. Compare an incident with deployment events and relevant logs.
  4. Inspect the evidence behind a suspected cause and decide what to investigate next.

Example: A service becomes slow after a release. Atlas shows a response-time increase near a deployment and related error messages. A future AI assistant could suggest what to inspect—but timing alone does not prove the deployment caused the slowdown.

Core capabilities

Health and uptime

Periodic checks, success/failure history, and clear service status.

Performance

Response-time trends and changes over time, not just a green/red badge.

Deployments and errors

Link release timestamps to failures, logs, and operational events.

Investigation workspace

Explore incidents interactively; later, add evidence-linked AI troubleshooting.

Proposed architecture

Collection: scheduled health probes and optional app-provided metrics, logs, or deployment events.

Backend: validate inputs, store timestamped results, calculate summaries, and expose an API.

Interface: a responsive status dashboard with charts and incident details; a chat-style investigation assistant could be added later.

Future AI: retrieve bounded, relevant logs and events; summarize evidence; propose checks; explicitly mark uncertainty.

Possible technologies (not decided)

Python or Node.js backend, a relational database for time-stamped checks, Docker, HTTPS, a charting library, and optional metrics/logging tools. Existing Docker/Traefik experience could help; do not introduce infrastructure until the first use case requires it.

Build it in stages

  1. First playable: monitor one app, store health checks, and chart response time and uptime history.
  2. Operational context: add deployment timestamps, error events, and basic filters.
  3. Multi-service view: compare services and create an incident timeline.
  4. Later: AI-assisted investigation with citations to actual logs, metrics, and events; optional notifications.

These are suggested milestones, not completed features.

Engineering challenges

False alarms: one failed probe may be a network hiccup. Design check frequency and status thresholds carefully.

Time and correlation: normalize timestamps and distinguish correlation from causation.

Data volume: bound log retention, query cost, and chart detail; avoid collecting secrets in logs.

Reliability: Atlas should make monitoring failures visible rather than silently showing stale green status.

Accessibility and mobile: status must not depend on color alone; tables, charts, and investigation controls need readable alternatives.

Evaluation and portfolio evidence

Simulate downtime, slow responses, failed deployments, and missing telemetry. Verify timestamps, alerts/status calculations, and that incident explanations cite the underlying events.

Show employers: API and database design, deployed monitor, test scenarios, metrics charts, security choices, incident walkthroughs, and an engineering log of decisions and fixes.

Relevant skills: backend development, Docker/deployment, observability, APIs, reliability, and eventually AI tool integration.

Status and open decisions

Status: future portfolio idea; no Atlas implementation is claimed.

Decide later: first monitored service, how to ingest deployment events, retention limits, what constitutes an incident, and when AI would genuinely save investigation time.

Guiding principle: collect trustworthy operational evidence first; add AI only when it improves diagnosis.
