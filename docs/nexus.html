Project Nexus

An interactive AI research workspace that connects documents, concepts, and evidence—so users can investigate knowledge rather than just ask a chatbot.

← Current roadmap · Concept stage · November 19, 2026

The problem

Research and technical information is scattered across documents. Search can find passages, but understanding how facts, systems, and ideas relate takes additional work. Standard document chat often returns a single answer without letting you explore those connections.

Goal: make large collections of information searchable, connected, inspectable, and backed by evidence.

Audience: researchers, students, developers, and teams investigating complex documentation. These are proposed users, not validated customers.

What a user could do

  1. Upload research papers, Markdown, technical manuals, project notes, or a codebase's documentation.
  2. Ask a question in plain language and see supporting passages and citations.
  3. Explore a graph of concepts, services, entities, and their relationships.
  4. Select a node or relationship to inspect the source evidence and ask follow-up questions.
  5. Compare conflicting documents, trace dependencies, and follow an investigation without restarting it.

Example: “What might break if we change our authentication system?” Nexus could retrieve relevant documentation, show dependent services, and explain possible impacts with links to the evidence. It must not present inferred dependencies as confirmed facts.

Three connected capabilities

1. Evidence-based RAG

Chunk and index documents; retrieve relevant passages; generate answers with citations and uncertainty when evidence is missing.

2. Knowledge graph

Represent entities as nodes and relationships as edges. Every extracted connection should carry a source and confidence or verification status.

3. Interactive investigation

Navigate relationships, open supporting documents, ask why a connection exists, and continue exploring related questions.

4. Evaluation and trust

Test retrieval, relationship extraction, citation accuracy, and whether the system distinguishes known facts from guesses.

Proposed architecture

Ingestion: upload → parse and clean → preserve document metadata → chunk → embed → index.

Graph extraction: detect candidate entities and relations → normalize names → link each edge to its evidence → verify or mark uncertain.

Question answering: interpret query → retrieve text and/or graph neighbors → assemble evidence → generate cited answer → display connected entities.

Interface: mobile-friendly chat plus an optional interactive graph and source viewer. A conversational interface can lead the experience without hiding structured evidence behind endless messages.

Possible technologies (not decided)

Next.js or another web framework; an embedding model; a vector store such as LanceDB or PostgreSQL with pgvector; a graph store such as Neo4j or a relational edge table; an LLM API for extraction and answers. Choose tools after testing a small prototype, not for their names alone.

Scope: build it in stages

  1. First playable: ingest a small document set, search it, and return answers with inspectable citations.
  2. Graph prototype: extract a limited set of relationships (for example, service → depends on → API) with source links.
  3. Interactive exploration: click a node, view evidence, and ask a follow-up grounded in that context.
  4. Later: conflicting-source comparison, saved investigation trails, multi-document analysis, and richer graph-assisted retrieval.

This is a suggested development sequence, not a commitment or implementation status.

Engineering challenges

Extraction accuracy: LLMs can invent entities or relationships. Require source spans, deduplicate entities, and flag uncertain edges.

Retrieval quality: chunking and similarity can omit key context. Compare keyword, vector, and graph-based retrieval on a labeled test set.

Conflicting evidence: preserve document dates and provenance; surface disagreement rather than quietly choosing a side.

Scale and usability: large graphs become cluttered. Filter by query, neighborhood, relation type, and evidence strength.

Privacy and security: handle uploads and access control carefully, restrict model/tool permissions, and establish retention/deletion rules.

Accessibility: the graph needs a keyboard-accessible alternative such as a relationship list; voice cannot be the only way to interact.

How to prove it works

Build a small benchmark with known questions, source passages, and expected relationships. Measure whether the correct passage appears, whether an answer is supported, and whether a graph edge is actually evidenced. Record failures and improvements.

Portfolio evidence: architecture diagram, ingestion pipeline, retrieval/graph evaluations, tests, deployment instructions, screenshots or demo, accessibility checks, and an engineering decision log.

Why employers may care: this combines full-stack development, ETL, search, graph modeling, AI integration, evaluation, observability, and product design. The value is in verifiable engineering—not just a chat wrapper.

Current status and decisions still open

Status: future portfolio concept; not yet built. Separate from the existing TaskNest RAG chatbot, which can serve as a learning foundation.

Open questions: first target audience and document type; graph extraction strategy; evidence verification rules; local versus hosted storage; whether the first interface should emphasize chat, graph, or both.

Guiding distinction: RAG finds relevant evidence. Graphs model explicit connections. Nexus brings both into an interactive investigation workspace.
